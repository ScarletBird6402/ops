# 환경 · GitHub 운영 (레포 티어 + 연출 + 새 환경 셋업)

> 2026-07-21 통합: 사외GitHub_운영방침.md + 새환경_셋업체크리스트.md → 이 문서. 원본은 _archive/.

> **성격:** 공개 GitHub의 운영·연출 정책 + 새 환경(디스크 교체 등) 셋업 절차.
> **핵심 원칙:** 연출은 **실체를 증폭**하되 **대체하지 않는다.** 엔지니어 독자에겐 스펙터클이 아니라 밀도·일관성·진정성이 곧 쇼맨십.

## 1. 레포 2티어 분리 (최상위 규칙, 2026-07-06 추가)
| 티어 | 레포 | 공개 정책 |
|---|---|---|
| **산출물** | swe-notes · ai-engineering-notes · swe-projects · 프로필 README | **상시 공개** — 클린 파이프라인 통과분만. "재직 중 자기계발" 서사로 이직 낌새 0 유지 |
| **운영(save-state)** | `ops`(비공개, 신설) — 핸드오프·마스터플랜 본부판·브리프·배정/세션 로그·프로젝트 킷 | **영구 비공개. 공개 전환 절대 금지** — 전환 시 전체 커밋 히스토리까지 노출됨 |

- 포트폴리오 = **산출물 레포**. save-state는 관제 문서라 공개할 이유 자체가 없음.
- "평소 비공개 → 필요 시 공개" 전략은 어느 티어에도 쓰지 않음(산출물은 상시 공개가 유리 — 커밋 서사·Pages, 운영은 금지).
- 로컬 클론 폴더를 티어별로 물리 분리, push 전 `git remote -v` 확인 습관.
- 에이전트가 만드는 로그·운영 문서는 ops 경로에만 커밋. 공개 레포 안에서 운영 문서가 발견되면 게시-검증 FAIL 조건.

## 2. 연출 원칙 (공개 GitHub 운영)

### 2.1 정체성 (한 줄 정의)
- 이 리포는 **"실무에서 배운 것을 꾸준히 문서화하는 IT/CS 지식베이스"** 다.
- 두 얼굴: (a) 나를 위한 **영구 참고 지식베이스**, (b) 남에게 보이는 **포트폴리오**.
- 톤: 과장 없는 학습 노트. "완벽한 레퍼런스"라 주장하지 않는다(진정성 = 신뢰).

### 2.2 사이트 구조 (GitHub Pages)
```
/(리포 루트)
├─ README.md          ← 프로필/입구(첫인상). 무엇·왜·어떻게 보는지
├─ index.html         ← 랜딩: 가치 한 줄 + 카테고리 맵(A~V) + 최근 추가
├─ A/ B/ ... Q/        ← 카테고리별 폴더(정본 HTML, 제목 기반 파일명)
└─ assets/            ← 공용 CSS 등(선택)
```
- 카테고리 폴더 = 마스터 플랜 A~V. 각 폴더에 카테고리 인덱스(간단).
- 파일명 = `코드 제목.html`(단일 규칙, 포트폴리오·학습 겸용). 상호링크도 동일. 코드 동결이 링크 안정성의 전제.

### 2.3 랜딩 페이지 구성
30초 안에 "무엇/범위"가 파악되도록, 담백하게:
1. **소개 한두 문장**(슬로건 금지): 무엇을·어떤 범위로 정리하는지 사실 서술.
   예: "웹 프론트엔드·백엔드·DB·인프라·보안·CS를 정리합니다. 업무 중 학습한 내용을 기반으로 계속 추가됩니다."
2. **형식 안내(사실 나열, PR 금지)**: 다루는 범위 / 언어(언어 중립 + C++·Python 관점 대조) / 업데이트 방식.
3. **카테고리 맵**: A~V를 6블록(클라이언트·서버데이터·설계품질협업·운영플랫폼·보안·CS통신)으로 그룹핑한 시각적 목차.
4. **최근 추가 5개**: 최신 문서 링크 → "살아있음" 신호.
> 대표작 미리보기·큐레이션은 두지 않는다(연출감). 범위·꾸준함·일관성이 스스로 말하게 둔다.

### 2.4 일관성 · 네비게이션 (진짜 프로덕션 밸류)
- **템플릿·스타일 100% 통일**(생성 프롬프트로 이미 강제) — 문서 수가 많을수록 일관성이 인상 요인.
- **상호링크(관련 문서)**로 위키처럼 엮기 → "더미"가 아니라 "지식 그물"로 보이게.
- 각 문서 상단에 카테고리·난이도 표시, 하단에 관련 문서. 빵부스러기(breadcrumb) 한 줄.

### 2.5 진정성 프레이밍 (anti-WWE 가드레일)
- 정직한 라벨: "학습 노트 / 지속 성장 중". 과장·허위 지표 금지.
- 출처·한계 명시할 것은 명시(예: "입문→심화 계단식, 5~6년차 상한 지향").
- **꾸며낸 스펙터클 금지**: 가짜 배지, 부풀린 통계, 의미 없는 애니메이션 등.
- **문서 단위 실무 맥락·경험담 명시 금지**: 비식별해도 제3자 해석·추론 위험. "실무 발원" 서사는 사이트 전역 소개 한 줄(집합적·추상적)로만 두고, 개별 사례로 내려가지 않는다 → 추론 단서 0.

### 2.6 게시 파이프라인 + 품질 게이트
게시 전 **3-체크**(공개 리포라 필수):
1. **비식별화**: 내부 시스템명·사내 코드·파일명·비공개 수치 0건. (공개 전 마지막 방어선)
2. **템플릿 준수**: 골격·스타일·병기 규칙 일치.
3. **링크 무결성**: 관련 문서 링크가 실제 파일명(제목 기반)과 일치.
- 통과 → 커밋. **커밋 위생**(원자적·의미 있는 메시지, ← I3 항목 그대로 실천)도 그 자체로 포트폴리오.
- 게시 주기: 보고 씨앗 → 정본 재생성 시점마다. 몰아서보다 **꾸준히**(그래프가 서사).

### 2.7 포트폴리오 연결
- **프로필 README**(GitHub 계정 레벨): 두 축을 함께 소개 — 이 지식베이스(폭·문서화) + AI SELD 리포(기술 깊이).
- 이력서·자소서에서 이 사이트로 링크. "IT활용능력·지속학습"의 증거로.
- 두 리포가 상호보완: **깊이(SELD) × 폭·꾸준함(지식베이스)**.

### 2.8 은근한 인상 요소 (연출 없는 연출)
따로 꾸미지 않고 "좋은 엔지니어의 습관"이 결과로 드러나게 하는 요소들.
- **상호링크 그물(강추)**: 관련 문서를 촘촘히 연결, 특히 카테고리를 가로지르는 링크(예: 백엔드 트랜잭션 ↔ DB 격리수준) → 연결된 사고 체계로 읽힘.
- **커밋 서사**: 원자적·의미 있는 커밋 메시지(I3 실천). 초록 그래프보다 메시지 품질이 아는 눈엔 더 인상적.
- **생각의 흔적**: 결론만이 아니라 트레이드오프·버린 접근·"흔히 헷갈리는 지점"을 남김. 단 **개념 자체의 함정**으로 서술(경험담·실무 맥락 아님 → 안전).
- **언어별 대조를 시그니처로**: C++·Python 관점 대조를 사이트의 일관된 형식으로. 소개엔 자랑이 아니라 형식 설명 한 줄.
- **정직한 미완성**: [신규·계획] 항목을 "예정"으로 노출 → 로드맵 있는 사람으로 읽힘. 다 채운 척보다 살아있고 정직.
> 폐기: "문서별 실무 맥락 한 줄" — 비식별해도 제3자 추론 위험이라 제외(§2.5).

### 2.9 하지 말 것 (요약)

- [ ] SourceTree 설치 시 Tools→Options→Git 탭의 Email도 noreply인지 확인
