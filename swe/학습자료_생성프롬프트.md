# 학습자료 생성 프롬프트 (재사용)

> **용도:** 마스터 목차의 엔트리 1개 → 완결 HTML 학습자료 1개 생성.
> **호출 시 채울 것(엔트리에서 복사):** 주제 / 핵심 키워드 / 맥락.

---

## 호출 템플릿

```
아래 규칙과 골격에 따라 학습자료 HTML 1개를 만들어줘.

- 주제: (예: I4 의존성 주입(DI)과 테스트 용이성)
- 핵심 키워드: (예: 생성자·setter 주입/외부 주입으로 mock 대체)
- 맥락: Vue3 프론트/Java 백엔드 등 웹개발 입문자 대상 범용 IT/CS 학습자료.
        시스템 특화 코드·내부 파일명 금지, 범용 예제로만.
- 파일명: 코드 + 주제 제목. (예: I4 의존성 주입과 테스트 용이성.html)
```

---

## 규칙 (온보딩)

웹개발·CS 입문자(주력 언어 C++·Python, 최근 Java·Vue)를 위한 학습자료. 아래 골격을 반드시 지킬 것.

### 산출물
- 형식: **완결된 단일 HTML 파일 1개**(주제 1개당). 마크다운 아님.
- **파일명 = `코드 제목.html` 단일 규칙** (예: `I4 의존성 주입과 테스트 용이성.html`). 레포는 포트폴리오·개인 학습 겸용 단일 운영.
  - "관련 문서" 상호링크도 이 파일명을 가리킨다 → GitHub Pages에서 작동.
  - 코드 체계는 동결(재사용 금지)이므로 파일명·링크가 안정적으로 유지된다.
- 언어: 한국어. 영어 병기는 아래 [영어 병기 규칙]을 따를 것. 코드·식별자는 영어, 그 외 다른 언어 금지.
- 스타일: GitHub 라이트 테마. 아래 CSS를 `<style>`에 그대로:
  - 본문 최대 폭 1000px, 가운데 정렬, 폰트 -apple-system/Segoe UI/맑은 고딕
  - 배경 #fff, 글자 #24292f, 테두리 #d0d7de, 코드 배경 #f6f8fa, 강조색 #0969da
  - blockquote 3종: 경고 노랑 #fff8c5 / 정보 파랑 #ddf4ff / OK 초록 #e6ffec
  - 표는 border-collapse + 짝수행 옅은 음영, pre/code는 monospace(Consolas/D2Coding)
  - flow 박스: 코드 배경+테두리, 가운데 정렬 monospace(흐름도용)

### 표준 골격 (이 순서로)
0. **한눈에 보는 결론** (불릿 4~6개, 언어 무관)
1~N. **개념 본문** — 반드시 "언어 중립"으로. 원리·Why·트레이드오프 중심
★ **언어별 대조**(핵심 섹션): 같은 개념이 각 언어에서 어떻게 나타나는지 표 비교
  - Java / JS·TS / Python / C++ (유사 언어는 묶기). **C++·Python 필수 포함**
  - C++(메모리·수명·ABI·컴파일 타임), Python 관점 통찰을 `backquote`로 덧붙임
- **함께 알면 좋은 것**: 인접 개념·심화·트레이드오프·유용 도구 5개 내외
- **한 장 요약**: 불릿 4~6개
- **관련 문서**: 함께 배우면 좋은 다른 주제 링크(**`코드 제목.html` 파일명으로**, 임의 파일명 금지)

### 내용 원칙
- "이렇게 써라"가 아니라 "이게 무엇이고 왜 이렇게 하는가"(학습 목적).
- 트레이드오프·안티패턴·흔한 함정(조용한 실패, N+1 등)을 반드시 짚을 것.
- **"흔히 헷갈리는 지점"** 을 짚되, **개념 자체의 함정**으로 서술(경험담·실무 맥락 아님).
- **소단원 유기적 연결(중요)**: 소단원을 독립 항목의 나열로 쓰지 말 것. 각 소단원은 앞 소단원에서 자연스럽게 이어지도록 구성한다.
  - 각 소단원의 **결론이 다음 소단원의 전제**가 되게 설계: 한 소단원이 남긴 질문·한계·"그렇다면 이건?"이 다음 소단원의 도입이 되도록.
  - 소단원 도입부에 앞 내용과의 연결 한 문장을 두거나("앞에서 X를 봤으니 이제 Y"), 문서를 관통하는 **하나의 축·예제·질문**을 잡아 전 소단원이 그 축의 다른 단면을 보여주게 한다.
  - 집필 순서 권장: 소제목만 먼저 나열 → 소제목들이 하나의 논리 흐름(문제 제기 → 원리 → 함정 → 대조 → 종합)을 이루는지 확인 후 본문 작성. 흐름이 끊기면 소제목 순서를 재배치.
  - 마지막 점검: 인접한 두 소단원을 이어 읽었을 때 논리적 도약이 없는지 확인.

### 영어 병기 규칙 (용어를 3분류하여 처리)
1. **개념어(번역 필요)** — 한국어 표준어가 있는 학술·설계 개념.
   → `한국어(영어)` 형태로 **최초 1회만** 병기, 이후 한국어(또는 표준 약어)만.
   예: 결합도(coupling), 의존성 주입(dependency injection), 제어의 역전(inversion of control, IoC).
2. **정착 외래어(병기 불필요)** — 한국어에 이미 굳어진 IT 용어. → 한국어만.
   예: 인터페이스, 클래스, 메서드, 테스트, 코드, 프레임워크, 컨테이너, 생성자, 필드.
   ※ 억지 번역어(예: 인터페이스→"추상 계약")를 괄호에 넣지 말 것.
3. **코드 토큰(식별자·키워드·API·번역어 없는 코드 관용어)** — 백틱 코드 서체.
   → 영문 병기·한국어 번역 모두 하지 않고, 문장에 자연스럽게 녹인다.
   예: `new`, `final`, `static`, `setter`, `getter`, `mock()`, `@Autowired`.
   ※ 번역어 없는 관용어(`setter` 등)는 프로즈 단어처럼 쓰지 말고 백틱으로 감싸 코드 토큰임을 드러낸다.

추가 원칙:
- 최초 1회 원칙: 개념어 병기는 첫 등장에만. 재등장 시 반복 금지.
- 자명성 필터: 한국어만으로 의미·검색이 충분하면 병기 생략(예: 굳이 "생성(new)" 식으로 쓰지 않음).
- 괄호 안에는 **표준 영어 원어만**. 잘 안 쓰는 번역어를 넣지 않는다.

### ★언어별 대조 심화 지침
- 독자는 C++·Python **문법은 알지만 내부 동작(메모리·컴파일·런타임 기제)은 낯선** 수준. 타깃 언어가 C++·Python이므로 이 둘은 **표에 더해 별도 소제목으로 깊이 있게** 서술.
- 고급 용어(vtable, ABI, 소유권, 덕 타이핑, Protocol 등)는 **쓰기 전에 한 줄로 풀어 설명**할 것. 단정적 나열 금지.
- C++·Python은 **짧은 코드 예제**를 각각 포함해 개념을 눈으로 보이게 할 것.
- Java/JS·TS는 표 + 한두 줄 요약으로 가볍게.

### 최신성 확인 (웹 검색 활용)
- 핵심 개념·원리는 안정 지식이므로 그대로 서술한다. 다만 **"함께 알면 좋은 것"·"흔히 헷갈리는 지점"** 처럼 도구·생태계·모범 사례가 걸린 부분은 그 사이 신규 기술로 개선점·변화가 생겼을 수 있다. 이런 지점은 **웹 검색으로 현재 상태를 확인한 뒤** 작성한다.
- 검색이 특히 유효한 경우: 특정 도구·라이브러리·표준의 현재 권장 방식, 과거의 흔한 조언이 지금도 유효한지(구식 안티패턴이 해소됐는지), 언어·런타임의 최신 버전에서 달라진 동작, 새 표준·API의 등장.
- 검색 결과 반영 시 규율:
  - **안정 지식 vs 최신 동향을 뒤섞지 말 것.** 원리는 원리대로 서술하고, 최근 변화는 "최근에는 …"으로 구분해 덧붙인다.
  - 특정 버전·연도에 의존하는 서술은 그 시점을 명시(예: "2020년대 중반 기준").
  - 검색으로 알게 된 내용도 **공개 리포 게시물**이므로 비식별·범용 원칙을 동일하게 적용. 특정 벤더·상용 제품은 대표 예시로만.
  - 확실치 않으면 단정하지 말고, 안정적으로 참인 수준으로만 서술한다(추측·환각 금지).
- 검색이 불필요한 경우(순수 원리·수학·언어 중립 개념)는 굳이 하지 않는다 — 판단해서 선별적으로.

### 게시 주의 (공개 리포)
- 내부 시스템명·사내 코드·비공개 수치·내부 파일명 절대 금지. 범용 예제로만.
- **문서에 실무 맥락·경험담 명시 금지**(비식별해도 제3자 추론 위험). 순수 개념 설명으로만.
